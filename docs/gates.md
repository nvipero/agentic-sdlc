# Gates and deployment

## Required checks

Required on every project PR:

- **`guards`** runs `main`'s definition on `pull_request_target` and reads the PR's commits and diff as data, never executing them; event values reach its script only through the environment. It fails on: a commit outside its role's paths or without a parsed `Factory-Role` trailer (spec-only commits excepted); a merge commit that is not a clean merge of `main`; a non-Conventional commit message; a branch not named `<type>/issue-<n>-<description>`; any change to `.factory/`, `.claude/`, `.github/`, `.devcontainer/`, `scripts/` or `CLAUDE.md`; changes to `tests/acceptance/` after the first implementer commit beyond the owner's `tests-change-approved` label events; for each `database` component, without the owner's `migration-approved` label event, a change to an existing migration or an added migration with a destructive or authorisation-weakening statement (`.github/scripts/migration-check.sh`: `drop`, `truncate`, `delete from`, a column type change, a rename, `drop policy`, `disable row level security`; a heuristic on the SQL, comments included). The implementer's paths include the `database` and `api` components' paths and their hosts' files, from `main`'s `.factory/config.yaml` (`components.sh`); an invalid `components` fails. It lists changed earlier tests, test configuration, new migrations with their grants, policies and `security definer` functions, and changes to the files the host descriptors list (`supabase/config.toml`) for "Where to look". The owner's own PRs get only a note.
- **`tests`** runs on `pull_request` with a read-only token and fixed commands (not the project's npm scripts): type check, unit tests, Deno tests for the components whose host tests them with Deno (`supabase` functions), when they have `*_test.ts` files (the paths come from the checkout's `components.sh`, which needs Ruby on the runner; the Deno pin and flags are fixed in the workflow), build (`unit-and-build`), and Playwright acceptance tests (`acceptance`). With a component on host `supabase`, `acceptance` first starts Supabase's local stack on the runner's Docker with the image's CLI version (pinned in the workflow), from the committed `supabase/supabase.lock`, with the database reset to the branch's migrations and seed (`.github/scripts/supabase-stack.sh`, the same script the container runs on the native runtime); the app and the tests get its addresses and demo keys through the environment.
- **`dependency-review`**: no new dependency with a high-severity vulnerability.
- **CodeQL** (default setup) through the ruleset: no high-severity alert.
- **Secret scanning** with push protection.
- **`label-audit`**: owner-only labels by anyone else are removed.

Test commands cannot be weakened from a PR: the workflow fixes them and the App cannot change workflow files.

## Preview

For a PR that is not a draft, `tests` uploads its build; `preview-deploy` runs `main`'s definition on `workflow_run` after `tests` passes, checks without any secret that guards passed on the same commit, then deploys only the build's static files in environment `preview` with the deployment target's secrets, never running PR code there. The target is the frontend component's `host` in `main`'s `.factory/config.yaml` ([components](architecture.md#components)), deployed by `.github/scripts/deploy/<host>.sh`: `vercel` or `cloudflare`. The build's files are deployed as static files only: no functions, routes or rules from the build (on `cloudflare`, `_headers`, `_redirects` and `.assetsignore` are dropped). One preview per PR at a stable address (`vercel`: `<owner>-<repo>-pr-<n>.vercel.app`; `cloudflare`: a Workers Preview at `pr-<n>-<repo>.<subdomain>.workers.dev`), shown in the PR's deployments panel (environment `pr-preview`, which holds no secrets), replaced on each push and removed when the PR closes (`preview-closed`, `preview-cleanup`). `vercel` previews need a Vercel login, and the Vercel token is scoped to the one project. `cloudflare` previews are behind Cloudflare Access, and the token is scoped to the one Worker. After deleting a closed PR's Preview, `cloudflare` checks that its address no longer serves it to the public and warns if it does (a known Cloudflare issue, see [risks](risks.md)).

## Production

`tests` also runs on every push to `main` (without dependency review) and uploads the build; `production-deploy` runs `main`'s definition on `workflow_run` after it passes, only for a push to `main`, only if the commit is still `main`'s head, and deploys the build's static files in environment `production` (deployable from `main` only, same secrets) to the production address (`vercel`: `<repo>.vercel.app`; `cloudflare`: `<repo>.<subdomain>.workers.dev`). Deploys queue rather than replace each other. After the deploy it checks that the production address serves the new deployment. Production is public. On `vercel`, a placeholder holds the production place before the first merge, because Vercel makes a project's first deployment production. On `cloudflare`, the placeholder comes from creating the Worker in setup, which the pipeline's token cannot do. With the frontend's `spa: true`, unknown paths serve `index.html` on `cloudflare`; `vercel` fails the deploy on it.

### Operating production

- **A failed run on `main`:** fix it with a new PR, or re-run the `tests` run with **Re-run all jobs**. **Re-run failed jobs** can leave the run without its build, and `production-deploy` then fails on purpose.
- **Rollback:** a revert PR, through the normal pipeline. For an emergency on `vercel`, **Instant Rollback** in the Vercel dashboard (on Hobby only to the previous production deployment; the first one returns to the placeholder). After a rollback Vercel stops moving production to new deployments, so the next `production-deploy` fails with "is the project rolled back?". Undo it in the dashboard (**Undo Rollback**); the pipeline's project-scoped token cannot. On `cloudflare`, **Rollback** in the Worker's deployments in the dashboard makes the earlier version a new deployment.
- **Old deployments:** on `vercel`, Vercel's deployment retention removes them (Hobby default: 30 days; the last three and the live one are kept). On `cloudflare`, a closed PR's Preview is deleted with its deployments; production versions stay in the Worker's history.
