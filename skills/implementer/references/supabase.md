# Host `supabase`

For components with `host: supabase` in `.factory/config.yaml`. The owner creates `supabase/` with `supabase init`; the Supabase CLI fixes the paths.

- **Database** (`supabase/migrations/`): migrations named `<timestamp>_<name>.sql`. Every new table in an exposed schema gets row level security and the policies the spec needs, and explicit, minimal grants per role (`anon`, `authenticated`, `service_role`): on Supabase a new `public` table is readable and writable through the API by any role with a grant. Secrets live in Vault, which the owner sets. A `security definer` function sets `search_path`.
- **Also yours** (`implementer_files` in `.github/scripts/hosts/supabase.yaml`, which the guards enforce): `supabase/config.toml` (auth, redirect URLs, `verify_jwt` per function) and `supabase/seed.sql`. `supabase/.gitignore` is the owner's.
- **API: Edge Functions** in `supabase/functions/<name>/index.ts`, Deno. Import dependencies as versioned `npm:` specifiers in the code (`npm:@supabase/supabase-js@2`), not through a function's `deno.json` or URLs: only npm is reachable, and one test run from the root must see every function. A function checks its caller (JWT, or `verify_jwt` in `supabase/config.toml`) unless the spec makes it public. Read secrets from the environment; the owner sets function secrets.
- **Browser calls to a function:** the function answers `OPTIONS` and sends the CORS headers itself, as on the hosted platform; the local stack does not add them.
- **The client** reads `import.meta.env.VITE_SUPABASE_URL` and `import.meta.env.VITE_SUPABASE_ANON_KEY` (or `VITE_SUPABASE_PUBLISHABLE_KEY`), never a literal address or key.
- **Acceptance tests run against the local stack:** at the repository root, in the same Bash call as Playwright, `env="$(bash .github/scripts/supabase-stack.sh native)" && export $env`, then the acceptance tests. It starts the stack from `supabase/supabase.lock` and resets the database to your migrations and seed, so a migration that does not apply fails here. The lock is the owner's: it pins the service versions, so a `supabase/config.toml` setting that changes them (`[db] major_version`) stops the stack; put it under `uncertain` instead. Studio, analytics and the pooler are not in the stack. If the script fails for any other reason, the environment is broken: say so in your return, do not work around it.
- **Their tests** in `supabase/functions/tests/<name>/<name>_test.ts` (`_test`, not `.test`, so Vitest never picks them up): `Deno.test` with `node:assert/strict`, external services and Supabase stubbed by replacing `globalThis.fetch`, never called. The root `deno.json` holds `{"nodeModulesDir": "none"}`, without which Deno looks for npm packages in the root's `node_modules`. Run them with `deno test --allow-env supabase/functions/`; commit the `deno.lock` it writes at the root, or the orchestrator's own test run leaves the work tree dirty.
